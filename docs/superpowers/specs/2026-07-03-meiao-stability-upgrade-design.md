# 梅奥MEIAO 整体稳定性升级 · 设计文档

日期:2026-07-03
状态:已与业主对齐,待实施计划
范围:本地测试版(`版本管理/梅奥MEIAO-当前版本`);云上生产版只做只读日志诊断,升级验证通过后才由业主决定提交

## 1. 背景与问题

程序早期开发时未考虑架构,实际使用中存在四类反复出现的问题(业主确认全部命中):

1. **任务卡死/状态不对**——任务卡在"处理中"、状态显示与实际不一致、失败不可见
2. **脏数据/无效数据**——历史占位数据、无效项目卡堆积
3. **交互逻辑别扭/卡顿**——操作无反馈、流程绕、页面反应慢
4. **功能时好时坏**——同一功能有时正常有时失效,修了又复发

**根因判断**:缺统一调度层。任务队列调度、模型调用调度、模块间协调三块都散落在各模块里(业主确认三块都有问题),同一件事有多份各自漂移的实现——这是"bug 修不完"的结构性根源。两个上帝文件加剧了这一点:`src/ShellMigratedApp.tsx`(约7900行)、`server/index.mjs`(约14500行)。

另有两项需求:
- **模型统一调度**(业主理想形态):所有板块的模型都在一处统一调度;模型有清晰分类(类型、流式、缓存命中、联网等),不同板块按需求匹配——如智能体对话要"流式+缓存命中",任务型调用要"直接拿结果"
- **前端视觉与交互体验**提升

智能工厂:业主接受建议——不做推倒式替代,维持"工厂=生产智能体,智能体中心=使用智能体"的分工,把没调通的链路修通。AI客服:本轮不做,后续单独立项。

## 2. 选定方案

**方案B:先立调度中枢,再逐模块迁移**(业主已确认,否决了"渐进加固"和"大重写"):

- 不推倒重来,先立两个中枢:**模型调度中心**(升级现有 `server/modelProviderRegistry.mjs`)+ **任务状态中枢**(收敛现有 `jobManager.mjs`/`appStateMerge.mjs` 判据)
- 然后一个模块一个模块把散落的私有逻辑收编进中枢,每迁一个模块 bug 面减一块
- 每步可本地实测验证,任何时候可停在稳定点

## 3. 约束与环境

- **本地测试版可以大改**,但动手前必须先做完整备份版本(`版本管理/梅奥MEIAO-备份版本-260703A`),可随时整体替换回去
- **云上版是生产**(腾讯云 111.229.66.247,`/www/wwwroot/meiao-internal`,PM2 进程 `meiao-internal`):只读诊断,不做任何写操作;发布仍走既有 `scripts/deploy_tencent.sh` 门禁(代码审查确认 + security:audit)
- **云上日志可用作诊断输入**:SSH 密钥 `~/.ssh/MEIAO.pem`;日志来源为数据库 `internal_logs` 表(保留7天)与 PM2 日志。用真实报错频次决定修复优先级
- **本地可实测**:环境齐全,可启动服务发真实请求验证
- **并行化**:相互独立的任务用子代理并行执行,压缩日历时间(详见第5节)

## 4. 分阶段设计

### 阶段0 · 备份与基线(前置,必须最先完成)

- 完整复制当前版本目录为 `梅奥MEIAO-备份版本-260703A`(排除 node_modules,复制后可 npm install 恢复)
- git 打 tag `baseline-260703`
- 跑通 `npm run lint / test / build`,记录基线状态;此后每阶段收尾要求同样全绿

### 阶段1 · 实测诊断体检(产出问题清单,是后续所有阶段的验收基准)

三路并行(子代理):

- **A. 云上日志诊断(只读)**:拉取 `internal_logs` 近7天数据 + PM2 日志,统计报错类型与频次,得出"实际最常发生的故障排行榜"
- **B. 本地实测巡检**:启动本地服务,逐板块发真实请求(一键主详、买家秀、视频、翻译、智能体对话、智能工厂);对"卡死/不生效"场景用运行态探针(写文件日志)钉死实际代码路径,不靠读代码猜
- **C. 脏数据审计**:扫描 `app_states.state_json` 等,统计占位值、无效记录的种类与数量(参考 `docs/cloud-update-data-cleanup.md` 已知垃圾卡形态)

产出:统一问题清单,按「调度类 / 数据类 / 交互类」归类,每条带复现步骤与线上频次。后续每阶段修完拿同一清单回归。

### 阶段2 · 模型调度中心(核心)

升级现有 `modelProviderRegistry.mjs`,不另起炉灶:

- **模型档案 schema**:每个模型一条档案——类型(chat/image/video/analysis/embedding)、能力标签(流式、缓存命中、联网、工具调用、任务型直出结果)、中转站与端点、参数格式、降级链
- **单一调度入口**:板块声明能力需求(如「流式+缓存的对话模型」「任务型生图模型」),调度中心返回模型+端点+参数格式;板块不再自己挑模型
- **统一管理界面**:前端全局设置页(`GlobalApiSettings.tsx`)改造为注册表唯一入口,所有板块用什么模型一处看、一处改
- **逐模块迁移**(顺序):智能工厂(试点)→ 智能体对话(流式+缓存类)→ 一键/买家秀/视频(任务型)→ 翻译等。每迁一个模块:先写输入对比探针验证新旧行为一致,再本地实测
- 判断中转站"支持/不支持某能力"时,遵守经验库铁律:多端点×多格式×多模型名穷举,核对返回实质

### 阶段3 · 任务状态中枢 + 脏数据治理(与阶段2部分并行)

- **单一状态机**:所有板块任务共用一套生命周期(提交→运行→成功/失败/取消)、一套卡死(stale)判据、一套失败判据;对现有 `jobManager.mjs`/`appStateMerge.mjs`/前端 adapters 里的多份判据做收敛统一,不重写
- **脏数据存量**:清理脚本先统计报告(清什么、清多少),业主二次确认后才执行;先备份数据
- **脏数据增量**:写入侧堵源头——占位值不落库,缺失用 `undefined` 表达(经验库既有规则推广到所有写入点)
- 验收:问题清单中"卡死/状态不对"条目全部关闭;失败任务可见失败原因;观察期内不产生新脏数据

### 阶段4 · 前端交互与视觉提升(在调度层稳定后)

先治本后治标——很多"卡顿/点了没反馈"是状态混乱造成的假死,阶段2/3已消除一部分:

- 第一轮:交互逻辑——操作即时反馈、流程顺滑、错误提示人话化(对照问题清单"交互类")
- 第二轮:视觉统一——间距/颜色/组件风格规范化
- 顺手拆分 `ShellMigratedApp.tsx`:按既有 `shell/modules` 模式,只拆本轮碰到的部分,不为拆而拆

### 阶段5 · 智能工厂理顺调通

- 维持"工厂生产智能体、智能体中心使用智能体"的分工;工厂已在阶段2作为模型调度试点接入中枢
- 逐条实测修通:知识库训练/检索、工具调用、预览试运行、发布流程
- 两个入口是否合并为一,留待稳定后由业主决定(纯 UI 改动)

## 5. 并行化策略

- 阶段1 的 A/B/C 三路子代理并行
- 阶段2 与阶段3 的**设计与判据梳理**可并行;涉及同文件改动时串行,避免冲突
- 阶段2 的逐模块迁移中,互不相关的模块可由子代理并行迁移(各自 worktree 隔离)
- 铁律:子代理转述的统计数字/调用关系,落地前主会话自行复核(经验库 6-13 条)

## 6. 全程纪律

- 每阶段收尾:`lint/test/build` 全绿 + 本地实测通过 → 业主人工确认 → 由业主决定是否提交云上
- 改"合并/现算/推导"类代码前,先写最小输入对比探针
- 排查链路 bug 先用运行态探针钉死实际代码路径,现象与静态推理冲突超过1~2轮立即上探针
- 硬编码字面量先 `git log -S` 反查引入 commit,有意 sentinel 升级不清理
- 阈值/容量参数一律 env + 保守默认
- 删除/清空类操作先统计报告并二次确认
- 每修完一类坑,按根因+修复+如何避免沉淀进对应层 CLAUDE.md

## 7. 验收标准(总)

1. 阶段1问题清单中「调度类」「数据类」条目 100% 关闭,「交互类」条目经业主确认关闭
2. 任务不再卡死在"处理中";失败任务展示失败原因
3. 所有板块模型调用走统一调度中心,全局设置页一处管理;换/加模型只改注册表
4. 观察期(本地使用一周)不产生新脏数据
5. 智能工厂五条链路(配置/知识库/工具/预览/发布)实测全通
6. `lint/test/build` 全绿,测试数量不少于基线
