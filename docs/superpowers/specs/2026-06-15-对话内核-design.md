## 2. 设计:补五个缺口(职责单一,可独立测试)

### 2.1 模型能力表(缺口1,单一来源)
- 新增 `server/modelCapabilities.mjs`:一张表,key = 模型 id(对齐 `jobRuntime.mjs` `AGENT_MODEL_CATALOG` 里的真实 id:`gpt-5-4-openai-resp`、`claude-sonnet-4-6`、`gemini-3.1-pro-openai`、`gemini-3-flash-openai`、`gemini-3-5-flash`),value = `{ contextWindowTokens, maxOutputTokens, supportsStreaming, supportsToolUse }`。
- `supportsToolUse` 本期不用,先登记,给第2期生图留位。
- 提供 `getModelCapability(modelId)`:命中返回该模型能力;未登记返回**保守默认**(小窗口 + 不假设支持流式)并 `log` 提醒(呼应"缺数据不阻塞、给保守默认"铁律)。
- 这是"换模型自动适配"(用户已选方案1)的唯一数据源。各模型上下文长度的具体数值在 plan 里填实(由我查证后给定,Codex 不臆造)。

### 2.2 上下文策略按模型自动适配(缺口2,纯函数)
- 新增 `server/contextPlan.mjs`,导出纯函数 `resolveContextLimits({ modelId, contextPolicy })` → 返回 `{ maxHistoryRounds, summaryTriggerThreshold, maxSummaryChars, maxOutputTokens }`。
  - **取值优先级**:用户在 `contextPolicy` 里**显式配置的值**(尊重既有配置)> 按 `getModelCapability(modelId)` 的上下文窗口**推算的自适应值** > 保守默认。
  - 即:用户没配 → 长模型给长历史、短模型给短历史,自动适配;用户配了 → 听用户的。
- **改造点(不重写,只换取值来源)**:`index.mjs:4392-4399` 三个 `|| 常量` 改成调 `resolveContextLimits(...)`;`providerGateway.mjs:2107` 的 `max_tokens` 4096 改成读传入的 `maxOutputTokens`(由本函数按模型给)。
- 摘要逻辑 `buildConversationSummary` **不动**,只是它的阈值参数改由本函数供给。摘要产物仍只用于本次发送,**不回写原始 `messages`**(占位铁律)。

### 2.3 后端→前端流式(缺口3)
- 对话端点 `/api/chat/sessions/{id}/messages` 增加流式响应模式:`runAgentConversation` 已有的 `onProgress` 回调 + 上游 `readProviderSseChatResponse` 增量内容,经 **SSE(`text/event-stream`)** 边收边推前端。
- **非流式路径保留**,生图等其它 `taskType` 继续走 `json()` 旧路,零回归。
- 上游不支持流式的模型(查能力表 `supportsStreaming`)自动回退:后端仍可一次性拿到再整段下发,前端表现为"整段到达",不报错。
- 前端 `internalApi.sendChatMessage` 从"等完整 JSON + 800ms 轮询进度"升级为读 SSE 流(进度事件 + 内容增量走同一条流,轮询可保留为不支持 SSE 时的兜底)。

### 2.4 前端展示成熟化(缺口4+5)
- **Markdown + 代码块**:助手消息渲染从纯文本 `whitespace-pre-wrap`(`ChatConversationPane.tsx:591`)升级为 Markdown 渲染(引入成熟 markdown 库 + 代码高亮),支持代码块、列表、加粗、链接、表格。代码块带**一键复制**。用户消息可保持纯文本(避免把用户输入误当 markdown)。
- **逐字打字机**:配合 2.3 的流式,助手消息边收边渲染(增量追加),替代现在"整段一次出现"。
- **消息操作工具栏**:接通已预留的 `renderMessageActions` 钩子(`ChatConversationPane.tsx:37,680`),给助手消息加**复制**、**重新生成**按钮。重新生成 = 用同一上文重发最后一轮。
- **上下文压缩提示(业主决定 2026-06-15)**:压缩触发时,前端在消息流插一条轻量系统提示行"较早的 N 轮对话已折叠为摘要",让用户知道模型"记得但非逐字记得"。提示是展示层信息,不写回原始历史。

### 2.5 实时状态(贯穿)
- 复用进度事件,本期对话状态:`thinking`(模型在想)→ `streaming`(逐字返回中)→ `done`/`error`,加 `compressed`(已折叠摘要,见 2.4)。经 SSE 同一通道下发。
- 本期状态仅限对话本身;生图、知识库等状态留给第2/3期往同通道加。

## 3. 数据流(一轮对话,流式)

```
用户发消息
  → 前端 sendChatMessage(历史 + selectedModel),建立 SSE 连接
  → 后端 createDbChatReply → runAgentConversation
       resolveContextLimits(selectedModel, contextPolicy) → 按模型给 保留轮数/摘要阈值/maxOutputTokens
       超阈值时 buildConversationSummary 压缩较早轮次(已有逻辑,只换参数来源)
  → providerGateway 按能力表决定真流式/回退,调上游
  → SSE 同一连接推:状态事件(thinking/streaming/done) + 内容增量 + compressed 提示
  → 前端逐字渲染(Markdown) + 实时状态;原始历史照常入库(摘要不回写)
```

## 4. 错误与兜底
- 上游超时/限流/抖动:复用现有重试退避(`jobRuntime` 既有模式);流式中断给前端明确 `error` 状态,不污染会话数据。
- 模型未登记:走保守默认能力,不崩。
- 摘要调用失败:降级为"只保留最近原文、丢弃更早轮次"并 `log`,绝不因摘要失败而整轮失败(沿用既有行为)。
- 上游不支持 SSE:回退整段返回 + 前端轮询兜底,不报错。

## 5. 测试(完工必须全绿)
- `modelCapabilities` 单测:已登记模型返回其能力;未登记返回保守默认。
- `resolveContextLimits` 纯函数单测:用户显式配置优先;未配时长模型给长历史、短模型给短历史;都缺走保守默认。
- 流式:SSE 增量被前端正确累积成完整消息;不支持流式的模型回退非流式;`json()` 非流式调用方(生图)零回归。
- 前端:Markdown/代码块正确渲染且不破坏纯文本消息;代码块复制、消息复制/重新生成可用;压缩提示行出现。
