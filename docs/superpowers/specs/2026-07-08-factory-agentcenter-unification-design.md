# 智能工厂 ↔ 智能体中心 打通(同一个智能体的两面)· 设计 spec

日期:2026-07-08 · 状态:业主已批准设计,待施工
范围:仅本地当前版本调试修改,**不上云**(发布上云由业主另行决定)

## 1. 背景与问题

阶段5-C(commit 8652b45)做了"发布同步桥":工厂发布 → 智能体中心物化一个草稿 agent + 迁移知识库文档。但它是**一次性**的:
- 重复发布时凭 `[智能工厂同步:factoryAgentId]` 描述文字标记找到已链接 agent,直接返回 `alreadyLinkedAgentId`,**什么都不更新**(`server/index.mjs:867`(本地)/`:897`(MySQL));
- 中心侧物化出来的是**草稿**,还要管理员再去中心手动验证+上线,两头跑;
- 中心侧可以随意编辑工厂出品的 agent,和工厂再次发布互相冲突;
- 关联标记藏在 description 文字里,是根因库"魔法字符串"反模式。

业主期望的最终形态:**同一个智能体的两面**——工厂=管理员制作/调试,中心=商家使用;一份真相在工厂,发布即对齐。

## 2. 业主拍板的三个决定

1. **形态**:保留两个入口,同一个智能体单一真相。工厂改完发布,中心自动更新,数据不再"只认第一次"。
2. **修改权归属**:工厂是唯一编辑入口。工厂出品的 agent 在中心不能改人设/模型/知识库(提示"去智能工厂修改"),中心只管上下线和使用。中心自建的老 agent 完全不受影响。
3. **发布门禁**:发布即上线。工厂点发布 → 自动跑中心验证门禁 → 通过直接上线商家可用;失败把原因报回工厂,线上维持旧版本,不留半成品。

## 3. 非目标(明确不做)

- **不合并两套存储模型**(工厂 config 单层 agent vs 中心 agent+versions):大手术、高风险、低收益;中心存储继续作为"发布视图"的物化载体。
- 不做中心→工厂的反向同步。
- 不改工厂仅管理员可见的入口策略(阶段5-A 维持)。
- 不动商家自建知识库、不动聊天运行时。

## 4. 行为规格

### 4.1 发布 = 对齐管道(upsert)

`POST /api/smart-factory/agents/{id}/publish`(双模式)升级:

- **无已链接 agent**:按现有 create 流程物化(agent+知识库+文档),然后自动验证;验证过 → 自动 publish 上线;验证失败 → 中心侧保持草稿不上线,失败原因(人话+技术详情,复用 S2 规范)报回工厂。
- **已有链接 agent**:
  1. 给该 agent 创建**新 agent_version**(system_prompt/模型/检索策略/知识库绑定,全部取工厂当前值)——复用中心既有版本机制,历史版本留痕;
  2. **全量刷新物化知识库**:以工厂当前文档为准替换链接知识库的文档并重新切片入库(ingestion 走中心既有管线);只动"当初由本桥物化的库",绝不碰商家自建库;
  3. 自动验证新版本;通过 → publish 新版本(线上切换);失败 → 新版本留验证失败标记、**老版本继续在线**,原因报回工厂。
- 发布响应带回:`agentCenterAgentId`、上线/失败状态、验证摘要。重复发布幂等(同内容再发布 = 建新版本上线,允许;不产生重复 agent/重复知识库)。

### 4.2 编辑锁(中心侧)

- 判据:agent 带结构化关联字段(见 §5)即"工厂出品"。
- 中心侧被锁接口:改人设/模型/知识库绑定/版本编辑类(agent PATCH 的内容字段、version 创建/编辑)→ 拒绝,结构化错误 `factory_managed_agent`,errorMessage="该智能体由智能工厂管理,请在智能工厂修改后重新发布"。
- **不锁**:上线/下线(publish/unpublish)、enabled 停启用、删除(删除走 §4.3 语义)、会话与聊天。
- 中心自建 agent(无关联字段)行为完全不变。

### 4.3 工厂删除已发布 agent

- 工厂删除时,若存在链接的中心 agent:前端二次确认文案明示"将同时在智能体中心下线该智能体(聊天历史保留)";确认后中心侧 agent **下线(unpublish/停用),不物理删除**,商家会话历史保留。
- 中心侧该 agent 的编辑锁在链接源消失后**解除**(变回普通 agent,管理员可自行处置)。

### 4.4 商家侧影响

- 正在进行的会话不中断;发布新版本后,下一条消息自动用新版本(中心现有"当前版本"机制天然如此)。

## 5. 关联标记:魔法字符串 → 结构化字段

- agent 增加结构化字段 `factoryAgentId`(MySQL:`agents` 表新列或既有 JSON 元数据字段;本地 JSON:agent 对象新属性,以施工时实际 schema 为准,双模式语义一致)。
- `findLinkedAgentCenterAgent` 改为**先查结构化字段,兼容回退 description 旧标记**;凡通过旧标记命中的,当场把 `factoryAgentId` 写回(惰性迁移),description 里的 `[智能工厂同步:xxx]` 从展示中清理。
- 新发布只写结构化字段,不再往 description 塞标记。

## 8. 测试与验收

**回归测试(新增):**
1. bridge:已链接 agent 再发布 → 生成更新计划(新版本字段 + 知识库全量替换),不重复建 agent/库;
2. 编辑锁:linked agent 的编辑类请求被拒(结构化错误),上下线/停启用放行;中心自建 agent 不受影响;
3. 关联判据:结构化字段优先、旧 description 标记回退命中+惰性迁移;
4. 双模式 source 测试:两套 handler 的发布/编辑锁/级联下线路径同步存在(沿用 U2 的 source 断言风格);
5. 验证失败路径:新版本不上线、老版本仍在线、失败原因结构化返回。

**本地 E2E 实测(验收基准):**
工厂建 agent→发布→中心出现且商家可聊→回工厂改人设+加知识库文档→再发布→中心同一 agent 回答体现新人设、检索命中新文档→中心尝试编辑被拒并提示→工厂删除→中心下线、会话历史还在。

**既有测试:** 前端/后端全量测试跑通,lint 0 error,tsc 干净,build 成功。
