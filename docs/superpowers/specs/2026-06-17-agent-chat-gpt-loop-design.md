# 智能体对话 GPT 化 Loop 升级 — 设计规格

> 日期：2026-06-17
> 前置：第1期对话内核、第2期生图工具调用、第3期知识库 RAG、第4期多工具增强，以及 2026-06-16 的 GPT 化首轮 UI/语义修复已完成。
> 目标：把智能体对话剩余 GPT 化改动组织成可自动化执行的闭环目标。每一批都必须包含计划、TDD、自动验证、浏览器验收、问题反馈、迭代修复、事实经验沉淀和提交记录。

## 0. 红线

- **禁碰**：`server/appStateMerge.mjs`、`src/adapters/shellPersistence.ts`，除非业主单独确认并补状态对账专项 plan。
- **禁新增“正则猜业务意图/状态”**。允许继续使用现有展示层 provider URL 清洗，只用于过滤协议噪音，不用于判断用户意图。
- **双 handler 同步**：凡是改 `server/index.mjs` 智能体 chat 逻辑，必须同步 MySQL handler（`createDbChatReply`/`getDbAgentVersionById`）和本地 JSON handler（`getLocalAgentVersionById`），并让测试覆盖两种 mode。
- **后端改完先重启再浏览器验证**：本地长跑进程可能仍在跑旧代码，验证前必须确认 `/api/health` 和日志来自新进程。
- **事实经验沉淀**：施工中真实遇到的问题、失败测试、浏览器验收异常、验证盲区、误判原因、修复方式和避免复发规则，都要在本批收尾沉淀。bug fix 同步外部诊断日志看板 `/Users/feiyanglin/程序开发/电商视觉一键化/云上日志诊断看板`；复发风险写入 `docs/agents/repeated-issues.md`，架构级根因写入 `CLAUDE.md`。
- **每批单独提交**：每个 Batch 至少一个计划内提交；反馈补丁若来自浏览器验收或线上日志，单独提交，提交信息说明来源。

## 1. 现状

已完成的能力：

- 上下文自适应、SSE 流式、Markdown 渲染、复制/重新生成消息操作。
- 模型 tool calling 生图，生图结果进入消息流。
- 知识库 RAG 和多工具统一：对话、生图、知识库、联网可以在 V2 工具链共存。
- 输入框已有 GPT 式能力栏：模型、附件、文件夹、生图、联网、思考强度。
- assistant run 已有统一折叠运行步骤。
- 历史生图 provider URL 已在展示/复制层隐藏。

剩余差距集中在四类：

1. **运行可靠性**：刷新、中断、失败恢复、重新生成、长耗时 pending run 的语义仍需要从“能用”收紧到“不会误导用户”。
2. **输入与能力状态**：能力栏已出现，但模型能力、思考强度、联网、生图、附件之间的动态约束还需要更像 GPT Web。
3. **运行观测与调试**：普通用户需要简洁主路径，管理员需要完整 tool/retrieval/provider 诊断链路，两者不能混在主聊天里。
4. **验收与经验闭环**：现在依赖人工记忆跑测试和浏览器检查，需要把“发现问题 → 反馈补丁 → 记录经验”变成固定 loop。

## 2. Loop 目标

每一批改动都必须跑同一个闭环：

```text
Define
  明确本批用户可感知目标、红线、涉及文件、验收样例
Test
  写失败测试，确认红灯；不允许先写实现
Build
  最小实现，不做跨批 refactor
Verify
  跑本批自动测试、相关回归、lint/build 或 Hermes 门禁
Observe
  刷新 localhost，做浏览器验收；必要时发真实测试消息
Feedback
  浏览器/日志/测试/人工反馈发现问题时，先确认事实与复现方式，再补失败测试，再做反馈补丁
Record
  提交、记录验证证据、沉淀本批真实遇到的问题与避免复发规则
Gate
  只有证据齐全才进入下一批
```

这个 loop 不是新增运行时代码，而是后续施工纪律。它的产物是：

- `docs/superpowers/plans/2026-06-17-agent-chat-gpt-loop.md` 作为后续施工图。
- 每批提交内包含测试、实现、验证记录。
- 每批结束时有明确的“通过 / 失败 / 进入反馈补丁 / 等人工确认”状态。
- 每批结束时必须回答：本批事实中遇到了什么问题、如何验证、如何修复、以后怎样避免；如果没有遇到问题，也要记录“未发现新问题”的验证依据。

## 3. 批次设计

### Batch A：对话运行可靠性

目标：发送、刷新、中断、失败、重新生成在普通聊天、生图、知识库、联网四类 run 上语义一致。

范围：

- 前端 pending run 展示和输入锁定。
- 中断/失败后的可见状态与可恢复动作。
- 重新生成保留原 run 的 `requestMode`、模型、联网、思考强度、附件。
- 本地 JSON 与 MySQL chat handler 的运行态字段一致性检查。

不做：

- 不改 provider 算法。
- 不改 app state merge。
- 不改知识库索引。

### Batch B：输入与能力状态 GPT 化

目标：输入框能力栏不仅可见，还要按当前模型、智能体配置、会话状态动态约束。

范围：

- 思考强度只显示当前模型支持的档位。
- 联网 pill 显示“可用/关闭/不可用原因”。
- 生图 pill 显示“开/关/当前模型最多输入图数量”。
- 附件与复用图片入口保持 `+` 主入口，但长文本不挤压发送按钮。
- Enter/Shift+Enter、IME 组合输入继续保持。

不做：

- 不改管理员模型白名单存储结构。
- 不引入新的设计系统。

### Batch C：assistant run 观测与管理员调试

目标：主聊天保留简洁运行步骤；运行视图成为调试入口，能定位 tool/retrieval/provider 失败。

范围：

- run trace 阶段标准化：thinking、retrieved、web_search、tool_calling、image_generating、done、error。
- 管理员运行视图展示 model、provider、tool 名、耗时、错误码、知识库命中摘要。
- 普通用户不看到 provider URL、内部 job id、API key、原始 function payload。
- 日志字段足够排查，但不泄露敏感内容。

不做：

- 不做新的独立日志平台。
- 不把 debug 信息塞进 assistant 正文。

### Batch D：真实对话验收矩阵与事实经验沉淀

目标：把“像不像 GPT、会不会复发”和“施工中真实遇到的问题如何进化修复”变成可重复验收的记录。

范围：

- 建立智能体对话验收矩阵：普通问答、生图、改图、知识库、联网、混合工具、失败恢复、重新生成。
- 每批浏览器验收后写入一条本地验收记录。
- 每批都写事实沉淀条目：问题事实、复现/验证方式、根因、修复、避免复发规则、相关 commit。
- bug fix 同步外部诊断日志看板。
- 复发经验写入 `docs/agents/repeated-issues.md` 或 `CLAUDE.md`。

不做：

- 不自动部署云上。
- 不把本地验收等同于线上已生效。

## 4. 证据标准

每批完成必须同时具备以下证据：

- **测试证据**：红灯输出、绿灯输出、相关回归输出。
- **静态证据**：`git diff` 只包含本批范围；红线文件未改；Hermes 门禁按需通过。
- **浏览器证据**：`localhost:3000` 刷新后的可见状态检查；涉及后端时确认服务重启后再验。
- **事实沉淀证据**：提供本批真实问题记录。若修复 bug，提供诊断看板记录、fingerprint、commit；若只是功能增强，提供验收记录路径和“未发现新问题 / 已发现并修复的问题”条目。

不能用以下内容当完成证据：

- “应该可以”
- 只跑单个测试来证明整批体验
- 只看 React source 来证明浏览器显示
- 只看本地通过来证明云上已发布

## 5. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 双 handler 漏改 | 每个涉及 `server/index.mjs` 的 Task 都要求 MySQL + 本地两条测试锚点 |
| 旧 provider URL 或内部 id 泄漏 | 展示/复制/运行视图各有 source 测试；浏览器验收搜索 `aiquickdraw.com/images` 和内部 job id |
| 视觉改动导致截断 | 每批浏览器验收包含窄屏/默认 viewport 的文本溢出检查 |
| 反馈补丁打乱批次 | 反馈补丁必须先记录事实、复现方式和失败测试，再单独提交 |
| 经验沉淀遗漏 | plan 收尾步骤固定写本批事实沉淀；满足复发/架构/bug 条件时同步 `docs/agents/repeated-issues.md`、`CLAUDE.md`、诊断看板 |

---

## 6. 验收口径

本设计通过后，执行计划应满足：

- 能按 Batch A → D 自动化施工。
- 每个 Batch 都有 TDD、验证、浏览器观察、问题反馈、迭代修复、事实经验沉淀步骤。
- 每个 Batch 都能独立提交和独立回滚。
- 对线上生产红线有明确保护。
- 不把“做计划”偷换成“已经实现剩余功能”；功能实现仍需按 plan 后续执行。
