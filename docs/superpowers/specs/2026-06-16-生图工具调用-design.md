# 第2期：生图工具调用 — 设计规格

> 日期：2026-06-16
> 前置：第1期对话内核已完成（Task 1-8，分支 `fix/chunk-error-boundary`）
> 范围：智能体对话中模型自主决定是否生图（原生 tool calling），保留生图模式作为引导入口，图片资产图谱
> 不碰：状态对账、知识库 RAG、多智能体、一键主图等其他模块逻辑

---

## 0. 红线

- **禁碰文件**：`appStateMerge.mjs`、`shellPersistence.ts`（状态对账文件）
- **禁新增正则猜状态**：不引入新的正则来判断"用户是否要生图"
- **旧路径不删**：未配置新中转站的智能体仍走 `kie_chat` + `buildImageConversationResult` 原路径
- **KIE 图像接口不动**：实际出图仍走 `kie_image`，本期只改对话/意图层

---

## 1. 目标

把当前"前端手动切生图模式 → 后端走独立生图路径"改造成 GPT 级体验：

1. **模型自主决定生图**：用户正常聊天，模型通过原生 tool calling 自己决定何时调用 `generate_image`
2. **生图模式变引导**：保留 UI 开关，但只在 system prompt 追加引导语，不再硬切后端路径；生图模式下需求不明确时模型先追问
3. **进度状态可见**：前端通过 SSE 展示"分析需求中… → 生成图片中… → 完成"
4. **图片资产图谱**：当前会话内所有图片（用户上传 + AI 生成）整理成目录注入 context，模型自然引用

---

## 2. 现状诊断

### 2.1 当前生图链路

```
前端 requestMode='image_generation' (用户手动切)
    → createDbChatReply 分流
    → buildImageConversationResult
        → buildImageGenerationAnalysisMessages (构造 prompt，让模型输出 JSON)
        → executeProviderJob kie_chat (模型分析，输出 taskType/prompt/inputImageUrls 等)
        → extractJsonObject 解析 JSON
        → agentImagePlan.mjs 正则兜底校验 (hasAgentImageReferenceIntent / shouldRequireAgentImageInput)
        → resolveAgentImagePlanInputUrlDetails (恢复逻辑，万一模型漏了输入图)
        → executeProviderJob kie_image (KIE 出图)
        → 返回结果
```

### 2.2 问题

- 用户必须手动切"生图模式"，不像 GPT 的自然体验
- 分析步骤已经在用 LLM 输出 JSON，但后面还有 `agentImagePlan.mjs` 的正则做兜底和恢复——散落多处，维护成本高
- 对话和生图是两条完全独立的路径（`runAgentConversation` vs `buildImageConversationResult`），无法在一次对话中自然切换

### 2.3 已验证

- 新中转站（`maxforai.top`，NewAPI 壳子，Codex 号池）支持 `gpt-5.4` 和 `gpt-5.5`
- 原生 tool calling 验证通过（`finish_reason: "tool_calls"`，参数解析准确）
- 模型名用点号格式：`gpt-5.4`、`gpt-5.5`
- 新中转站不支持图片生成 API，出图仍走 KIE

## 3. 架构设计

### 3.1 整体数据流

```
用户发消息
    │
    ▼
后端 createDbChatReply
    │
    ├─ 智能体配置了 toolCallingProvider?
    │     │
    │     ├─ 是 → runAgentConversationV2（新流程，本期新增）
    │     │
    │     └─ 否 → 走原路径（runAgentConversation / buildImageConversationResult）
    │
    ▼
runAgentConversationV2
    │
    ├─ 1. 上下文管家（复用第1期：摘要 + 近 N 轮 + 附件）
    ├─ 2. 注入图片资产目录到 system prompt
    ├─ 3. 构造 tools 定义（generate_image）
    │       - imageGenerationEnabled=false → 不传 tools，退化为纯对话
    │       - imageMode=true → system prompt 追加生图引导语
    ├─ 4. 流式请求新中转站（stream: true + tools）
    │     │
    │     ├─ finish_reason: "stop"
    │     │     → 纯文字，流式 SSE 推前端
    │     │
    │     └─ finish_reason: "tool_calls"
    │           → SSE: tool_calling（"分析需求中…"）
    │           → 解析 generate_image 参数
    │           → 校验 input_image_urls
    │           → SSE: image_generating（"生成图片中…"）
    │           → 调 KIE kie_image（复用现有逻辑）
    │           → SSE: image_ready（图片 URL）
    │           → 构造 tool result → 回传模型
    │           → 模型生成最终回复 → 流式 SSE
    │
    └─ 5. SSE: done
```

### 3.2 新增 Provider：openai_compatible

`providerGateway.mjs` 新增函数，走新中转站的 `/v1/chat/completions`。

```js
// 配置来源：环境变量
OPENAI_COMPATIBLE_API_KEY   // 新中转站 API key
OPENAI_COMPATIBLE_BASE_URL  // 默认 https://maxforai.top
OPENAI_COMPATIBLE_MODELS    // 允许的模型列表，逗号分隔：gpt-5.4,gpt-5.5

// 与现有 provider 的关系
kie_chat              → KIE 的 /v1/chat/completions（对话，无 tool calling）
kie_image             → KIE 图像 API（出图，不变）
openai_compatible     → 新中转站 /v1/chat/completions（对话 + tool calling）← 新增
```

核心能力：
- 支持 `tools` + `tool_choice` 参数
- 支持 `stream: true` 流式响应
- 处理流式中的 `tool_calls` delta 拼装
- 超时、重试、错误处理对齐现有 `kie_chat` 的模式

### 3.3 路由决策

`createDbChatReply` 里的路由逻辑改造：

```
当前：
  requestMode === 'image_generation'
    ? buildImageConversationResult(...)    // 生图路径
    : runAgentConversation(...)            // 对话路径

改造后：
  hasToolCallingProvider(version)
    ? runAgentConversationV2(...)          // 新统一路径（tool calling 自动分流）
    : requestMode === 'image_generation'
      ? buildImageConversationResult(...)  // 旧生图路径
      : runAgentConversation(...)          // 旧对话路径
```

## 4. Tool 定义

只声明一个工具，保持简单。

```json
{
  "type": "function",
  "function": {
    "name": "generate_image",
    "description": "生成或编辑图片。当用户需要创建新图片、修改已有图片、换背景、局部重绘等任何图片操作时调用。",
    "parameters": {
      "type": "object",
      "properties": {
        "prompt": {
          "type": "string",
          "description": "完整的生图提示词，包含主体、场景、风格、色调等描述"
        },
        "task_type": {
          "type": "string",
          "enum": ["new_image", "edit_image"],
          "description": "new_image=从零生成新图，edit_image=基于已有图片修改"
        },
        "input_image_urls": {
          "type": "array",
          "items": { "type": "string" },
          "description": "edit_image 时必填，要编辑/参考的图片 URL，从会话图片目录中选取"
        },
        "aspect_ratio": {
          "type": "string",
          "enum": ["auto", "1:1", "4:3", "3:4", "16:9", "9:16"],
          "description": "图片比例，默认 auto，仅在用户明确指定比例时修改"
        }
      },
      "required": ["prompt", "task_type"]
    }
  }
}
```

后端自动补全的参数（不需要模型填）：
- `selectedImageModel`：从 `version.modelPolicy.multimodalModel` 读取
- `resolution`：从图像模型能力表读取默认值
- `transparentBackground`：默认 false，后续可扩展

## 5. 图片资产图谱

### 5.1 数据收集

复用现有 `buildConversationImageCatalog(attachments, priorMessages, maxReferenceImages)`，扩展返回结构：

```js
// 现有：返回 [{url, name, source, mimeType, ...}]
// 扩展为：
{
  index: 1,                    // 稳定序号（整个会话内不变）
  url: 'https://...',
  label: '图1',
  name: '产品正面图.jpg',
  source: 'user_upload',       // 'user_upload' | 'ai_generated'
  mimeType: 'image/jpeg',
  generatedFrom: [3],          // AI 生成的图：基于哪些图的 index（从 imagePlan.inputImageUrls 推导）
  messageIndex: 5,             // 来自第几条消息
}
```

### 5.2 注入 System Prompt

格式化为文本追加到 system prompt 末尾：

```
## 当前会话图片目录

你可以在调用 generate_image 时引用以下图片的 URL：

图1: [用户上传] 产品正面图.jpg — https://...
图2: [用户上传] logo.png — https://...
图3: [AI生成] 第1次生成结果 — https://...
图4: [AI生成] 第2次生成结果（基于图3修改）— https://...

引用规则：
- edit_image 时，input_image_urls 必须从本目录中选取
- 用户说"原图""上一张""图1"等指代时，对照本目录理解
```

### 5.3 URL 校验

后端收到 `generate_image` 的 `input_image_urls` 后，校验每个 URL 在图片目录中存在。不存在的 URL 直接丢弃（不报错中断），避免模型偶尔幻觉出不存在的 URL 导致整个请求失败。

## 6. 生图模式引导语

前端 `imageMode: true` 时，在 system prompt 追加：

```
你正处于生图模式。用户希望你帮助生成或修改图片。
- 如果用户需求清晰（有明确的主体、风格或修改要求），直接调用 generate_image 工具
- 如果需求不够明确（缺少关键信息），先追问用户，不要猜测生图
- 你可以结合对话上下文理解"继续调整""按上一版改"等指代
```

`imageMode: false`（默认模式）时不追加，但 tools 定义仍然传——模型在自然对话中如果判断需要生图，仍然可以自主调用。

## 7. SSE 事件设计

复用第1期的 SSE 基础设施（`/api/chat/sessions/:id/messages` 端点），新增事件类型：

| 事件类型 | payload | 触发时机 | 前端展示 |
|----------|---------|----------|----------|
| `thinking` | `{ phase: 'thinking' }` | 请求发出 | "思考中…" |
| `streaming` | `{ delta: '...' }` | 模型输出文字 chunk | 逐字显示 |
| `tool_calling` | `{ tool: 'generate_image', args: {...} }` | 模型返回 tool_calls | "分析需求中…" |
| `image_generating` | `{ model: 'gpt-image-2' }` | KIE 出图请求发出 | "生成图片中…" |
| `image_ready` | `{ imageUrl: '...', imagePlan: {...} }` | 出图完成 | 显示图片 |
| `streaming` | `{ delta: '...' }` | 模型最终回复 chunk | 图片下方逐字显示总结 |
| `compressed` | `{ foldedRounds: N }` | 上下文压缩时 | "已压缩 N 轮历史" |
| `done` | `{ ... }` | 全部完成 | 完成状态 |

前端处理伪代码：

```js
eventSource.onmessage = (event) => {
  const { type, ...data } = JSON.parse(event.data);
  switch (type) {
    case 'streaming':     appendDelta(data.delta); break;
    case 'tool_calling':  showStatus('分析需求中…'); break;
    case 'image_generating': showStatus('生成图片中…'); break;
    case 'image_ready':   showImage(data.imageUrl); break;
    case 'compressed':    showCompressedHint(data.foldedRounds); break;
    case 'done':          finalize(data); break;
  }
};
```

## 8. 数据库与持久化

### 8.1 助手消息格式

生图消息的 metadata 增加 `imagePlan` 字段（与现有格式兼容）：

```json
{
  "role": "assistant",
  "content": "已帮你生成一张橘猫在阳台晒太阳的图片...",
  "metadata": {
    "requestType": "tool_calling",
    "toolCalls": [{
      "name": "generate_image",
      "args": { "prompt": "...", "task_type": "new_image", "aspect_ratio": "auto" }
    }],
    "imagePlan": {
      "requestMode": "tool_calling",
      "taskType": "new_image",
      "selectedImageModel": "gpt-image-2",
      "inputImageUrls": [],
      "prompt": "...",
      "size": "auto",
      "resolution": "1K"
    },
    "imageUrl": "https://...",
    "selectedModel": "gpt-5.4",
    "promptTokens": 1200,
    "completionTokens": 300,
    "latencyMs": 8500
  }
}
```

### 8.2 图片目录的持久化

图片目录不额外持久化——每次请求时从 `priorMessages` 实时构建。生成的图片 URL 已经在 `metadata.imageUrl` 和 `metadata.imagePlan` 中持久化，下次请求时从历史消息中提取即可。

## 9. 智能体版本配置变更

`modelPolicy` 新增字段：

```js
{
  // 现有字段
  defaultModel: 'gpt-5.4',           // 对话用的模型（改为新中转站支持的模型）
  cheapModel: 'gpt-5.4',             // 低成本模型
  multimodalModel: 'gpt-image-2',    // 出图模型（仍走 KIE）
  imageGenerationEnabled: true,

  // 新增
  toolCallingProvider: 'openai_compatible',  // 非空时走新流程
}
```

`toolPolicy` 不变——现有的 `linkedModuleInterfaces`（如 `one_click_main` 的 handoff）继续工作。tool calling 的 `generate_image` 是后端注入的，不存在 `toolPolicy` 里。

存储：`toolCallingProvider` 存在已有的 `model_policy_json` 列里（与 `defaultModel`、`multimodalModel` 同级），不需要新增数据库列或迁移。

## 11. 兼容性与降级

| 场景 | 行为 |
|------|------|
| 智能体未配 `toolCallingProvider` | 走原路径，完全不受影响 |
| 新中转站不可用 | `runAgentConversationV2` 抛错，前端显示"对话服务暂时不可用" |
| 模型未返回 tool_calls 但用户在生图模式 | 正常显示文字回复（模型判断不需要生图，可能在追问） |
| 模型 tool_calls 参数格式异常 | 忽略该次 tool call，回退为文字回复，log 告警 |
| KIE 出图失败 | 构造 tool result `{error: "图片生成失败: ..."}` 回传模型，模型回复用户说明失败原因 |
| `input_image_urls` 中有不存在的 URL | 静默丢弃，用剩余有效 URL 继续；全部无效则 tool result 报错 |

## 13. 不做的事（显式排除）

- **不做多工具**：本期只有 `generate_image` 一个 tool。第3期知识库 RAG 可能加 `search_knowledge`，第4期多智能体可能加更多，但现在不预设。
- **不做连续多次生图**：一条消息最多触发一次 `generate_image`，避免成本失控。
- **不删旧路径**：`buildImageConversationResult` / `agentImagePlan.mjs` 保留，供未迁移的智能体使用。
- **不做图片编辑 UI**：前端不加画笔/裁剪等编辑工具，所有修改意图通过自然语言表达。
- **不迁移所有智能体**：本期只在配置了 `toolCallingProvider` 的智能体上启用，逐步迁移。
