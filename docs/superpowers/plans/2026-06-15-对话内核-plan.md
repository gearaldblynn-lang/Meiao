## Task 2:上下文策略按模型自适应(纯函数)

**目标:** 把写死的 `||6`、`||10`、`||1200`、`||4096` 替换成"按模型上下文窗口自适应 + 用户配置优先"的纯函数。本 Task 只建函数 + 测试,**不接线**(接线在 Task 3)。

**Files:**
- Create: `server/contextPlan.mjs`
- Test: `server/contextPlan.test.mjs`

**取值优先级(三层):**
1. 用户在 `contextPolicy` 里**显式配置**的值 → 用它(尊重既有配置)。
2. 没配 → 按 `getModelCapability(modelId).contextWindowTokens` **自适应推算**。
3. 模型未登记(保守默认)→ 给保守的小配置。

**自适应推算规则(基于 token 计数,不用正则):**
- 触发压缩阈值占比、保留输出 token 占比做成 env + 保守默认。GPT-5.x 超 272K 输入会 2 倍计费,故默认压缩阈值锚定在远低于上限处。

- [ ] **Step 2.3:实现** `server/contextPlan.mjs`

```js
import { getModelCapability } from './modelCapabilities.mjs';

// env 旋钮 + 保守默认(锚定模型上下文窗口,取保守占比)
const HISTORY_BUDGET_RATIO = Number(process.env.CTX_HISTORY_BUDGET_RATIO || 0.5);   // 历史最多占窗口的比例
const SUMMARY_TRIGGER_RATIO = Number(process.env.CTX_SUMMARY_TRIGGER_RATIO || 0.6); // 占用超此比例触发压缩
const AVG_TOKENS_PER_ROUND  = Number(process.env.CTX_AVG_TOKENS_PER_ROUND || 800);  // 估一轮多少 token(保守高估)
const MAX_SUMMARY_CHARS_CAP = Number(process.env.CTX_MAX_SUMMARY_CHARS || 1200);

const toPosInt = (v) => {
  const n = Number(v);
  return Number.isFinite(n) && n > 0 ? Math.floor(n) : null;
};

// 纯函数:同一输入稳定产出。不读库、不改入参。
export const resolveContextLimits = ({ modelId, contextPolicy = {} } = {}) => {
  const cap = getModelCapability(modelId);
  const policy = contextPolicy || {};

  // 自适应基线(按窗口推算)
  const usableForHistory = Math.floor(cap.contextWindowTokens * HISTORY_BUDGET_RATIO);
  const adaptiveRounds = Math.max(6, Math.floor(usableForHistory / AVG_TOKENS_PER_ROUND));
  const adaptiveThreshold = Math.max(10, Math.floor(adaptiveRounds * SUMMARY_TRIGGER_RATIO));

  // 用户显式配置优先,否则自适应,最后保守默认
  return {
    maxHistoryRounds:        toPosInt(policy.maxHistoryRounds)        ?? adaptiveRounds,
    summaryTriggerThreshold: toPosInt(policy.summaryTriggerThreshold) ?? adaptiveThreshold,
    maxSummaryChars:         toPosInt(policy.maxSummaryChars)         ?? MAX_SUMMARY_CHARS_CAP,
    maxOutputTokens:         toPosInt(policy.maxOutputTokens)         ?? cap.maxOutputTokens,
    modelCapability:         cap,
  };
};
```

> 注:`adaptiveRounds` 上限实际由历史真实长度决定(Task 3 接线时,真实历史不够长就不会触发压缩);这里给的是"允许保留多少轮"的上界。若 1M 窗口算出的轮数过大,可在 env 设 `CTX_AVG_TOKENS_PER_ROUND` 调高来收敛——逻辑不变,只调数字。

## Task 4:后端流式(SSE)下行通道

**目标:** 让对话端点 `/api/chat/sessions/{id}/messages` 支持 SSE 流式返回。上游已有流式解析 `readProviderSseChatResponse`;本 Task 把"增量内容 + 状态事件"边收边推前端。**非流式路径保留**(生图等继续走 `json()`)。

**Files:**
- Modify: `server/index.mjs`(对话路由约 7763-7801;`runAgentConversation` 的 onProgress/输出接缝;`setChatProgress` 约 4839)
- Test: `server/chatStreaming.test.mjs`(新建,测纯函数部分)

**实现要点(顺现有 fetch/SSE 风格,不引 SDK):**
- 当请求带 `Accept: text/event-stream`(或 body 里 `stream:true`)时,响应头 `Content-Type: text/event-stream`,用 `res.write('data: ...\n\n')` 逐块推;否则维持现状 `json(res,201,result)`。
- 事件类型(对齐 spec 2.5):`thinking` → `streaming`(每个内容增量)→ `compressed`(压缩发生时,带"折叠 N 轮"信息)→ `done`(带完整 assistantMessage)/`error`。
- 复用 `runAgentConversation` 已有的 `onProgress` 回调:把它产生的进度 + 上游增量,转成 SSE 行。
- 抽一个纯函数 `formatChatSseEvent(type, payload)` 便于单测(不直接测 res 流)。

```ts
export type ChatStreamEvent =
  | { type: 'thinking' }
  | { type: 'streaming'; delta: string }
  | { type: 'compressed'; foldedRounds: number }
  | { type: 'done'; assistantMessage?: unknown }
  | { type: 'error'; message?: string };

export const parseChatSseChunk = (
  chunk: string,
  opts?: { withRest?: boolean },
): ChatStreamEvent[] | { events: ChatStreamEvent[]; rest: string } => {
  const parts = chunk.split('\n\n');
  const rest = parts.pop() ?? '';
  const events: ChatStreamEvent[] = [];
  for (const part of parts) {
    const line = part.trim();
    if (!line.startsWith('data:')) continue;
    try { events.push(JSON.parse(line.replace(/^data:\s*/, ''))); } catch { /* 跳过坏行 */ }
  }
  return opts?.withRest ? { events, rest } : events;
};
```
