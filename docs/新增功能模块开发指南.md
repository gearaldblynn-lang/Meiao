# 新增功能模块开发指南(梅奥 MEIAO · 当前版本)

> 本文档基于对当前版本源码的系统通读整理,目标:**当你要新增一个功能模块(例如再加一个"XX 生成"),照本文逐层改动即可端到端跑通**。
>
> 说明:
> - 文中 `文件:行号` 是编写时的定位锚点。这个仓库文件大、且暂无 git,**动手编辑前请用编辑器搜索对应符号名复核一次行号**(符号名比行号稳定)。
> - 全项目**没有"模块注册中心"这一单一真相源**,一个模块的定义散落在 3~5 张各自独立的表里,**漏改任何一张都会白屏 / undefined / 点不进去**。本文的价值就在于把这些散点一次列全。

## 一、整体架构与数据流

```
用户操作
  │
  ├─(选模块)──────────────────────────────────────────────┐
  │  侧栏 SidebarNavigation → activeModule                  │
  │                                                          ▼
  │                                            render switch(ShellMigratedApp)
  │                                            → <XxxModule/>(薄封装 ProjectListView)
  │
  ├─(填参数/传素材)── BottomInputBar ── onParamChange/onUploadMaterial
  │                                    → inputStateByScope[module:subFeature]
  │
  └─(点生成)── handleGenerate(按 activeModule 分派)
                 │
                 ├─ 策划型(one_click / translation):runShellXxxPlanning → arkService.generateXxx → 出方案(planning 状态)
                 │
                 └─ 出图型:runShellXxxWorkflow(shellWorkflow.ts)
                        │   组装 prompt/素材/config;需要 AI 出方案的再调 arkService.generateXxx
                        ▼
                     createInternalJob / processWithKieAi  ── 提交到后端通用 job 系统(/api/jobs)
                        │   payload 里塞 shellProjectId/subFeature/batchIndex/setIndex...(前后端唯一契约)
                        ▼
                  ┌───────────────── 后端(server) ─────────────────┐
                  │ jobManager:通用 job 表,按 taskType 分派,不认模块  │
                  │ 出图完成 → 结果写回 job 记录                        │
                  └───────────────────────────────────────────────────┘
                        │
   刷新/回填 ◄───────────┘
      │  shellDataAdapter.mapJobs(job→project,强按模块分组)
      │  shellDataAdapter.mapPersistedState(xxxMemory→project,强按模块重建)
      │  两边 by-id 合并 → 过滤删除墓碑 → 展示
      ▼
   持久化:前端写 xxxMemory → 后端 appStateMerge.mergeAppStateForStorage(强按模块键合并)入库
   删除:  persistedDeletion.pruneXxxMemory + 删除墓碑
```

**一句话总结分层**:
1. **前端注册渲染层**(声明模块、进侧栏、能显示)
2. **输入层**(底部输入栏的参数/素材)
3. **生成调度 + AI 服务层**(点生成 → workflow → AI/出图 → 提交 job)
4. **持久化 / 恢复 / 删除层**(结果落库、刷新重建、删除)
5. **后端层**(job 通用;仅"独立 memory 块"才需改合并)

关键设计取向:**后端 job 系统对模块完全通用**;**前端的注册、渲染、恢复、删除、合并全部"强按模块硬编码分支"**。所以新增模块的绝大部分工作量在前端。

## 三、逐层详解与"填空式"清单

### 层 1 — 前端注册与渲染

一个模块从"声明"到"界面能显示",按依赖顺序有 6 个必碰点(以现有 `BUYER_SHOW` 为范例)。

**① 枚举声明**(成对)— `src/types.ts`
```ts
// AppModule 枚举
BUYER_SHOW = 'buyer_show',
// AppModuleObj 镜像(业务代码几乎只用这个;漏了到处 undefined)
BUYER_SHOW: AppModule.BUYER_SHOW,
```

**② 中文名** — `src/ShellMigratedApp.tsx` 的 `MODULE_NAMES`(约 1224-1237)
```ts
[AppModuleObj.BUYER_SHOW]: '买家秀',
```
toast、项目标题都读它,漏了会显示 `undefined素材上传失败` 之类。

**③ 侧栏注册**(独立第二张表!)— `src/shell/components/layout/SidebarNavigation.tsx` 的 `MAIN` 数组(约 19-30)
```ts
{ module: AppModuleObj.BUYER_SHOW, icon: <Users size={20} strokeWidth={1.5} />, label: '买家秀' },
```
图标来自 `lucide-react`(文件顶部 import)。设置类模块放 `BOTTOM` 数组。**这张表最容易漏,因为不在主文件里。**

**④ 子功能 tab** — `src/ShellMigratedApp.tsx` 的 `MODULE_SUB_FEATURES`(约 1267-1313)
```ts
[AppModuleObj.BUYER_SHOW]: [
  { id: 'image', label: '买家秀图片' },
  { id: 'copy',  label: '纯文案', description: '待制作', disabled: true },
],
```
`getDefaultSubFeature` 取 `[0].id` 作默认;`disabled:true` 会被"待制作"拦截。**即使只有一个子功能也要建一项**,否则默认子功能回落成 `'default'`,scope key 与后端/持久化对不齐。

**⑤ 懒加载 import** — `src/ShellMigratedApp.tsx`(约 70-83)
```ts
const BuyerShowModule = lazy(() => import('./shell/modules/BuyerShow/BuyerShowModule'));
```

**⑥ render 分发** — `src/ShellMigratedApp.tsx` 的 `switch (activeModule)`(约 7385-7536)
```ts
case AppModuleObj.BUYER_SHOW:
  return <BuyerShowModule
    projects={filteredProjects}      // 已按 module+subFeature 过滤
    tasks={filteredTasks}
    subFeatures={MODULE_SUB_FEATURES[AppModuleObj.BUYER_SHOW]}
    activeSubFeature={activeSubFeature}
    onSubFeatureChange={handleSubFeatureChange}
    onDeleteResult={handleDeleteResult}
    onDeleteProject={handleDeleteProject}
    onRegenerateResult={handleRegenerateResult}
    onRecoverResult={handleRecoverResult}
    onCancelTask={handleCancelTask}
    pendingActionKeys={pendingActionKeys}
    showGenerationProgress={showGenerationProgress}
  />;
```
`default: return null`,不加 case 就白屏。**所有数据与 handler 都在这里注入模块。**

**模块组件本身**是薄封装,别写业务逻辑 — `src/shell/modules/BuyerShow/BuyerShowModule.tsx`(全文 ~33 行),`RetouchModule.tsx` 结构完全相同,是最佳复制模板:
```ts
const BuyerShowModule: React.FC<Props> = (props) => (
  <ProjectListView {...props}
    title="买家秀"
    description="生成真实感买家秀场景图……"
    emptyIcon={<Users size={30} strokeWidth={1} />}
    emptyTitle="生成买家秀"
    emptySubtitle="输入产品信息……" />
);
```
列表/结果 UI 全在通用 `ProjectListView` 里,新模块不用写。

### 层 2 — 输入层(BottomInputBar)

底部输入栏在 `ShellMigratedApp.tsx`(约 7562-7588)挂载。注意 `AGENT_CENTER / AI_CUSTOMER_SERVICE / SMART_FACTORY` 三类"对话/工作台"模块**不显示输入栏**(输入自理)。

模块特有内容都在 `src/shell/components/layout/BottomInputBar.tsx` 的按模块分派表里:

- **快捷参数(底部下拉)** `QUICK_PARAMS`(约 126-149):
  ```ts
  [AppModuleObj.BUYER_SHOW]: [
    { key: 'target', label: '含模特', options: ['含模特','仅静物'], defaultValue: '含模特' },
    { key: 'count',  label: '4张', options: ['1','2','4'], defaultValue: '4', allowCustom: true },
    { key: 'market', label: '中国', options: ['中国','美国', ...], defaultValue: '中国', allowCustom: true },
  ],
  ```
  参数依赖其它状态的(如精修比例依赖模型),写成函数并在 `getQuickParamsForContext`(约 568-570)里挑选。
- **扩展参数(展开面板)** `EXTENDED_PARAMS`(约 239-269)。
- **占位文案** `MODULE_PLACEHOLDERS`(约 824-833)+ `getPlaceholderForContext`。
- **生成按钮文案** `getGenerateLabelForContext`(约 854-861)。
- **素材类型(上传弹窗)** 两级:优先 `getMaterialTypesForContext`(约 593-599,如 `BUYER_SHOW → ['product','atmosphere','model']`);未命中回落 `UploadTypeSelector.tsx` 的 `MODULE_MATERIALS`(约 36-45,key 是模块字符串如 `'buyer_show'`)。新增素材种类要改 `MaterialType` 联合类型 + `ALL_MATERIALS`(label/icon)。

**参数如何变成 params**:控件改值 → `onParamChange(key,value)` → `handleParamChange`(约 7338-7355)写入 `inputStateByScope[scopeKey].params`(scope = `module:subFeature`)。点生成 → `handleGenerate` 读当前 scope 的 params → 过 `normalizeParamsForGeneration(module,subFeature,params)`(约 1428-1455,各模块有归一分支)→ 素材经 `ensureMaterialRemoteUrls` 上公网 → 打包派发。

### 层 3 — 生成调度 + AI 服务

**入口**:`ShellMigratedApp.tsx` 的 `handleGenerate`(约 3319)。开头锁定 `targetModule = activeModule`、`targetSubFeature = activeSubFeature`。

**它不是干净的 switch,而是一串 `if / else if` 分派**。workflow 函数**懒加载**:
```ts
const { runShellBuyerShowWorkflow, runShellImageGeneration, runShellRetouchWorkflow, runShellVideoGeneration }
  = await loadShellWorkflowModule();   // 约 4580
```
出图分派主干(约 4581-4851):
- `VIDEO` → `runShellVideoGeneration`
- `BUYER_SHOW / RETOUCH / EVERYTHING_REPLACE` → 批量分支,带 `onSpecialItemCompleted` 逐张回调
- `else`(主图/翻译出图/小红书封面等)→ `for` 循环按 `batchCount` 逐张 `runShellImageGeneration`

**"策划"阶段与"出图"阶段是分开的两套分派**:
- `ONE_CLICK` 策划:`runShellOneClickPlanning`(约 4296),产出 `plans`,项目进入 `'planning'` 态,用户选方案后再出图。
- `TRANSLATION` 策划分析:`runShellTranslationPlanningAnalysis`(约 3896/4059)。
- 选中方案再出图的 handler:约 6099/6276/6349/6752,把 `schemeContent` 塞进 `taskMetadata` 后调 `runShellImageGeneration`。

> 枚举命名注意:界面层用 `AppModuleObj.*`,workflow 层(`shellWorkflow.ts`)用 `AppModule.*`,同一套值。

**`runShellXxxWorkflow` 统一入参** `ShellGenerateInput`(`shellWorkflow.ts` 约 51-62):
```ts
interface ShellGenerateInput {
  module: AppModule; subFeature?: string;
  prompt: string;                                 // 用户需求文本
  params: Record<string,string>;                  // 前端表单参数(全 string)
  materials: Record<string, ShellMaterialInput[]>;// 按角色:product/styleRef/reference/logo/atmosphere/model/scene...
  signal: AbortSignal;
  apiConfig?: GlobalApiConfig;
  taskMetadata?: Record<string, unknown>;         // 透传到 job/prompt:shellProjectId/schemeContent/batchIndex...
  onJobCreated?: (jobId, providerTaskId?) => void;// 拿到后端 jobId 的进度回调
  publicBaseUrl?: string;
}
```

**两种出参形态**:
- 单张出图型(`runShellImageGeneration`)→ `ShellWorkflowImageResult`(约 89-107):`imageUrl / status('completed'|'generating'|'error') / taskId / backendJobId / prompt / creditsConsumed / message`。
- 批量型(`runShellBuyerShowWorkflow`/`runShellRetouchWorkflow`)→ `{ results: ShellWorkflowImageResult[]; creditsConsumed? }`,并用 `onItemCompleted(item, index, total)` 逐张回填 UI。

**两种出图策略(重要区别)**:
- **异步 job 型(买家秀)**:`submitBuyerShowImageJob → createInternalJob({ module, taskType:'kie_image', provider:'kie', payload:{...taskMetadata, imageUrls, prompt, model, aspectRatio}, maxRetries:2 })`(约 1054-1082),**提交完不等结果**,立刻回填 `status:'generating'` 占位,`onJobCreated?.(jobId)` 通知,后续由 job 同步机制回填。
- **同步等结果型(精修)**:`processWithKieAi(...)` `await` 直接拿最终 `imageUrl`(约 1957-1974)。

**AI 方案生成** `src/services/arkService.ts`:各模块 `generateXxx` / `analyzeXxx`(如 `generateBuyerShowPrompts`、`analyzeRetouchTask`)。返回结构约定为 `{ status:'success'|'error', tasks:[], message?, ... }`,**失败返回 `{status:'error', tasks:[], message}` 而不是抛异常**;调用方(workflow)判 `status!=='success' || tasks.length===0` 再决定是否 throw。AI 调用本身也走后端 job(`taskType:'kie_chat'`)。

**填空清单(本层)**:
1. 需要 AI 出方案 → `arkService.ts` 加 `generateXxx(...)`(签名参照 `generateBuyerShowPrompts`,返回 `{status,tasks,message}`)。
2. `shellWorkflow.ts` 加 `runShellXxxWorkflow(input, helpers, onProgress?)`;出图 job 的 payload 里塞全 `taskMetadata`(见层 4 契约)。
3. `ShellMigratedApp.tsx` 的 `handleGenerate` 分派处(约 4581-4851)加 `else if (targetModule === AppModuleObj.XXX)` 调用它;若懒加载模块要在 `loadShellWorkflowModule` 解构里加上函数名。
4. `normalizeParamsForGeneration`(约 1428)加本模块的参数归一分支。

### 层 4 — 持久化 / 恢复 / 删除

**应用状态结构** `src/utils/appState.ts` 的 `PersistedAppState`(约 57-70):**"每模块一个 memory 块 + 一个通用 `shellProjects` 数组"** 双轨。现有独立块:`translationMemory / oneClickMemory / retouchMemory / buyerShowMemory / videoMemory / xhsCoverMemory`,外加删除墓碑 `shellDraft`。持久化键 `AIGC_APP_STATE_V1`。

**回填机制(关键)**:job **不直接写 memory**;读取时由 `shellDataAdapter.mapJobs`(约 1284-2387)**实时把 job 映射成 project**,再与持久化 project by-id 合并。`mapJobs` 强按模块分组:万物替换 groups、**买家秀 groups(约 1436-1547,按 `-set-N` 拆套、`-missing-N` 补缺失批次)**、翻译 groups、一键主详策划 groups,其余走通用单 job 兜底(约 1740+)。结果 URL 取值很宽容:`getResultUrls`(约 253-285)从 10+ 字段搜刮 URL,新模块只要结果 URL 落在其一即可被识别。

**前后端唯一契约**:提交 job 时把 `shellProjectId / shellProjectName / subFeature / batchIndex / batchCount / setIndex / setCount / imageIndex / imageCount` 全塞进 `payload`(买家秀见 `shellWorkflow.ts` 约 1174-1197)。`mapJobs` 就靠这些字段分组和排序。

**刷新恢复** `shellDataAdapter.mapPersistedState`(约 932-1123):**每模块一段硬编码重建**。买家秀:`buyerShow.sets` 每 set 一 project(约 1073-1080);精修:`retouch.tasks` 每 task 一 project。新模块必须在此加自己的重建分支(否则 memory 里历史结果刷新后不显示),常用 `projectFromItems` / `projectListFromItems` 即可。

**删除** `src/utils/persistedDeletion.ts`:`prunePersistedAppStateForDeletion`(约 207-244)对每个 memory 块调各自的 `pruneXxxMemory`(如 `pruneBuyerShowMemory` 约 88-110)。匹配靠 `matchesTarget`(约 33-46),候选 id 集合硬编码:`id/taskId/backendJobId/providerTaskId/kieTaskId/projectId/whiteBgTaskId/lastTaskId`。新模块结果对象的标识字段须落在这个集合内,否则删不掉。

**填空清单(本层)** — 仅当用独立 `xxxMemory` 块:
- `appState.ts`:`PersistedAppState` 加字段(约 57-70);写 `createDefaultXxxState()` 接进 `buildPersistedAppState`(约 1075-1092);`normalizeLoadedPersistedAppState`(约 782-1019)加 normalize 分支(含 File/Blob 清洗、model 归一)。
- `shellDataAdapter.ts`:`MODULE_LABELS/MODULE_VALUES/VALID_MODULES`(约 132-156)加模块;`normalizeJobSubFeature`(约 632-686)加子功能识别;`mapPersistedState` 加重建段;job 需分组时 `mapJobs` 加分组桶并在通用兜底处跳过已分组 job。
- `persistedDeletion.ts`:写 `pruneXxxMemory` 接进返回对象(约 228-243)。
- 若复用 `shellProjects`,以上大多可免。

### 层 5 — 后端(server)

**结论:job 系统对模块完全通用,新模块通常不用改后端**;**唯一例外是引入了独立 `xxxMemory` 键 → 必须改 `server/appStateMerge.mjs`**。

- **通用、无需改**:
  - `server/jobManager.mjs`:`createJobRecord`(约 336)只存 `module/taskType/provider/status/payload_json` 通用列;去重 `findReusableJobSubmission`(约 147-176)按 `userId+module+taskType+provider+序列化 payload` 匹配,`normalizeReusablePayload`(约 28-37)只剔 `requestId`/`__creditReservation`。
  - `server/index.mjs`:`prepareStateForStorage`(约 996-1025)通用(compact → 超阈值 trim → 资产清理);`scrubDbJobPayloadBeforeSubmission`(约 3060-3065)通用。
  - 大小阈值 `APP_STATE_MAX_BYTES`(`index.mjs` 约 990-994):env 可配,默认 **4 MiB**(锚定 MySQL 16 MiB packet 的 1/4,历史教训)。
- **必须改(仅独立 memory 块)** `server/appStateMerge.mjs`:`mergeAppStateForStorage`(约 837-897)对每个 memory 块**显式点名深合并**;顶层是浅合并 `{...existing,...incoming}`(约 841-843)。**新键漏接 = 并发/多端写入时该模块数据被整块覆盖丢失,删除墓碑也不作用**。同时按需改 `applyDeletionTombstones`(约 223-293)、`collectTrimmableBuckets`(约 120-134)。可复用合并原语 `mergeProjectArrayByStableKeys`(约 701-732)。

## 四、决策树:复用 shellProjects,还是独立 memory 块?

```
新模块的结果结构是否复杂?
(多套/多子功能/多阶段策划/需要跨刷新精细合并)
        │
   ┌────┴─────┐
   否          是
   │           │
复用 shellProjects        独立 xxxMemory 块
(通用数组)               (仿 buyerShowMemory)
   │                        │
后端零改动                 必改 appStateMerge.mjs 合并
appState/deletion 免改      + appState 三处 + deletion + dataAdapter 重建
恢复走通用映射             恢复走自建重建分支
   │                        │
 推荐给"一图进一图出"       用于买家秀/一键主详这类
 的简单模块                复杂模块
```

**建议**:先默认走 `shellProjects` 通用路线;确实装不下(像买家秀的多套分组)再上独立 memory 块。

## 五、完整实操示例:新增一个 `FOO`("氛围图生成")模块

假设做一个最简单的"一图进一图出、无多套、无策划"模块,**走 shellProjects 通用路线**(后端零改动)。

**1. 声明枚举** — `src/types.ts`
```ts
// AppModule 枚举里
FOO = 'foo',
// AppModuleObj 镜像里
FOO: AppModule.FOO,
```

**2. 中文名** — `ShellMigratedApp.tsx` `MODULE_NAMES`

## 六、踩坑清单(务必过一遍)

**注册一致性**
- 枚举(types.ts)、中文名(MODULE_NAMES)、侧栏(SidebarNavigation.MAIN)、子功能(MODULE_SUB_FEATURES)是**四张互相独立的表,没有单一真相源**,漏一处就白屏 / undefined / 点不进去。**SidebarNavigation 不在主文件里,最容易漏。**
- 全项目用 `AppModuleObj.XXX` 引用,新增务必补 `AppModuleObj` 镜像,别只加裸 `AppModule` 枚举。
- 每个模块**至少一个子功能**,否则默认子功能回落 `'default'`,scope key 与后端对不齐。
- 反面教材 `PHOTOGRAPHY`:声明了枚举但全链路没接线,是僵尸枚举,别模仿。

**子功能命名**
- 存在两套并存的子功能定义:强类型 enum(`BuyerShowSubMode` 等)与 UI 字符串表 `MODULE_SUB_FEATURES`,**二者 id 不对齐**(买家秀 UI tab 是 `image/copy`,enum 是 `integrated/pure_text`)。**UI 与生成 scope 实际只认 `MODULE_SUB_FEATURES` 的字符串 id。** 新模块建议 tab id 直接对齐后端约定,别再造第二套。

**生成/持久化(项目历史血泪)**
- **占位/fallback 值绝不当真值持久化**:缺字段优先返回 `undefined`,展示侧兜底;要识别历史占位,收敛到**单一判据**(现有 `normalizeModel` + `LEGACY_MODEL_PLACEHOLDERS`),禁止用魔法字符串散落到合并/写入/展示各处。
- 代码里的硬编码字面量比对(如 `-missing-N`、`LEGACY_POLLUTED_TRANSLATION_MARKERS`、`isOneClickPlanningPlaceholderText`)**多是历史修 bug 引入的有意 sentinel,不是可清理的脏代码**。改动前先查它的来由(本仓库暂无 git,是待补前置)。
- 后端 `mergeAppStateForStorage` 顶层是浅合并,**独立 memory 键漏接 = 并发写覆盖丢数据**。
- **前后端各有一份几乎同名同逻辑的归一/合并函数**(`normalizeProjectLikeItem`、`isStalePlanningFailureResult` 等前端 `shellDataAdapter.ts` 与后端 `appStateMerge.mjs` 各一份)。新模块若加特殊归一,**两边都要改**,否则出现"前端显示对、入库后又变样"。
- 大字段(base64 图 / dataURL)别塞进持久化:`compactAppStateForStorage` 会剥离内联预览,新模块遵循同样约定。

**通用纪律**(本项目 CLAUDE.md)
- 动"现算/合并/推导"类代码前,先写最小输入对比探针(同一输入喂前端 `buildShellDataSnapshot` 与后端 `mergeAppStateForStorage`),验证一致再动手。
- 小步改、立刻 `tsc` 类型检查(`tsc -b` / `npx tsc --noEmit -p tsconfig.app.json`,注意根 tsconfig 是 references-only,检查 src 要用 `tsconfig.app.json`)。
