# 买家秀模块 · 重写开发文档

> 目标读者：一个负责**推倒重写买家秀实现**的 AI / 工程师。
> 这不是新增第二个买家秀，而是**把现有买家秀的实现整个换成干净的新代码**——入口仍是原来那个「买家秀」，最终只保留一个买家秀。
> 你不需要读懂旧买家秀的全部代码，本文把「要做成什么」「能复用什么」「要避开什么坑」一次讲清。
> 开发期可以把新实现临时放在并列文件里做对比验证，但**验收通过后要用新实现替换旧实现、删掉旧代码**，不留第二个入口。
> 项目：梅奥 MEIAO 内部工具（`meiao-internal`）。前端 React18 + TS + Vite，主壳 `src/ShellMigratedApp.tsx`；后端 Node `server/index.mjs` + 自建任务队列 `server/jobManager.mjs`；AI 走「号池」(OpenAI 兼容中转)。

## 0. 一句话定位

买家秀 = **用 AI 生成"仿真买家秀"图**：把「产品图」当主体，「模特图」当使用产品的人，「场景参考」当环境背景，生成一批看起来像真实买家拍的使用场景图（UGC 风格）。

它**不是一次点一下就出图的按钮**，而是一条 **两阶段流水线**：
1. **策划阶段**：调分析模型，为这一套生成一整套「拍摄方案」（每张图一段提示词，第 1 张是基准图，后面的图都要跟基准图保持一致性）。
2. **出图阶段**：按方案逐张提交生图任务。

一次生成可以有**多套**，每套 = **一种产品**，各套独立配置、独立出图、独立展示。

## 1. 为什么重写（重写而非打补丁）

旧买家秀（live 版在 `src/adapters/shellWorkflow.ts` + `src/shell/components/layout/BottomInputBar.tsx` + `src/shell/modules/BuyerShow/`）积累了 7 个已知问题（见第 9 章），且和共享输入栏、共享素材状态深度耦合，在老代码上直接改风险高、容易把功能改崩。

**策略：把买家秀的实现推倒重写成干净代码，然后替换旧实现——入口仍是同一个「买家秀」，最终只有一个买家秀。**
- 仍复用 `AppModule.BUYER_SHOW` 这个枚举和侧栏那个「买家秀」按钮，**不新增第二个模块/按钮**。
- 新实现拥有自己干净的组件、工作流、数据结构、UI，**只复用底层原语**（出图任务提交、素材上传、任务队列、结果展示 `ProjectListView`）。
- 开发期为了对比验证，可以先把新实现放在并列的新文件里（比如带 `V2`/`Rebuilt` 后缀），跑通后**把「买家秀」入口切到新实现，并删除旧买家秀代码**。最终产品里只有一个买家秀。

> ⚠️ 开工前先给项目初始化 git 并提交基线（目前无 git、无自动化测试），否则替换出问题时回滚困难。这也是"开发期先并列、验证后再替换删除"能安全进行的前提。

## 2. 参数规格（已和业主定稿，按此实现）

### 2.1 全局设置（整次生成共用，不分套）
| 项 | 说明 |
|---|---|
| **目标市场** | 单选一个国家/市场（如 美国 / 日本 / 东南亚…）。整次生成共用，不按套区分。影响策划阶段的语言、人物长相、场景风格。 |
| **含模特 / 仅静物 开关** | 保留这个开关。开=画面里有人物；关=纯静物（无人脸/无人体，允许出现手做使用演示）。 |

### 2.2 每套设置（"套 = 一种产品"，各套独立）
| 项 | 数量上限 | 必选? | 作用 |
|---|---|---|---|
| **产品图** | ≤ **5** 张 | ✅ 必选 | 画面主体，AI 要"用上这个产品"。 |
| **模特图** | ≤ **1** 张 | ⭕ 可选 | 给 AI 参考，生成一个**相似**（不是一模一样）的模特。没传就按「目标市场 + 文字要求」生成人物。 |
| **场景参考** | ≤ **4** 张 | ⭕ 可选 | 给 AI 参考，生成一个**相似**的场景/环境背景。没传就按市场/文字要求生成场景。（旧代码里叫"氛围图 atmosphere"，V2 对用户展示统一叫"场景参考"。） |
| **本套文字要求** | 一段文本 | ⭕ 可选 | 每套可**单独**写这套的额外要求（比如动作、风格、卖点）。 |
| **本套出图张数** | 数字 | ✅ | 这套生成几张图，每套可不同。 |

> 定稿数字：**产品 ≤5 / 模特 ≤1 / 场景 ≤4**。"含模特"开关保留；目标市场全局单设不分套。
> "相似不等于一模一样"：模特图/场景图都是**给 AI 做参考**，产出的是相似的人/场景，做不到完全复刻——文案里别承诺"一致"。

### 2.3 生成时的兜底规则
- **无模特图** → 按「目标市场 + 本套文字要求 + 产品图」生成人物。
- **无场景参考** → 按市场/文字要求生成场景。
- **仅静物（开关关）** → 画面无人物。
- 产品图是唯一必选项；模特/场景都可选。

## 3. 用户流程与 UI（第 2 章：界面规格）

> 这是"重写后的买家秀界面长什么样、用户怎么点"的规格，是给你照着写组件的蓝图。

### 3.1 整体布局
沿用壳层现有布局：主区展示结果（复用 `ProjectListView`），底部/侧边是配置区。新实现建议**不复用共享的 `BottomInputBar`**（那是旧实现的耦合源），而是做一个**独立配置面板**（可以是右侧 Sidebar 或底部展开区，跟随项目现有视觉风格）。

### 3.2 配置面板结构
```
┌─ 买家秀 配置面板（重写后） ────────────────────┐
│ 【全局】                                        │
│   目标市场:  [下拉单选 ▾]                        │
│   含模特:    [开/关 开关]                        │
│                                                 │
│ 【套 1 · 产品A】                       [删除本套] │
│   产品图  (≤5):  [＋上传]  [缩略图][缩略图]...    │
│   模特图  (≤1):  [＋上传]  [缩略图]              │
│   场景参考(≤4):  [＋上传]  [缩略图]...           │
│   本套文字要求:  [多行文本框]                    │
│   本套出图张数:  [数字输入]                      │
│                                                 │
│ 【套 2 · 产品B】                       [删除本套] │
│   ...（结构同上，独立配置）                      │
│                                                 │
│            [＋ 添加一套]                         │
│                                                 │
│            [开始生成]                            │
└─────────────────────────────────────────────────┘
```

### 3.3 关键交互
1. **添加一套**：点「＋ 添加一套」→ 新增一个套卡片，`setIndex` 递增。套与套之间配置完全独立。
2. **删除一套**：每套卡片右上「删除本套」→ 移除该套及其素材。删除要二次确认（防误删已传素材）。删除后其余套的展示序号重排（但内部标识要稳定，见第 5 章）。
3. **上传素材（每套 × 每类型独立）**：
   - 每套内，产品图 / 模特图 / 场景参考各有独立的「＋上传」按钮。
   - 点上传 → 系统文件选择器（`accept="image/*"`，产品图/场景 `multiple`，模特图单选）。
   - 选完 → 调 `uploadShellMaterial` 上传（见 4.2），拿到 URL，落进**这一套、这一类型**的素材列表。
   - 上传的每张素材必须带上「属于哪套(`setIndex`) + 哪类型(product/model/scene)」的归属标记——**这是旧模块 P1/P2 的最大坑：归属不清导致多套坍缩。V2 必须从上传那一刻就把归属钉死。**
   - 达到上限（产品5/模特1/场景4）后「＋上传」置灰。
4. **已上传预览**：每套卡片内按类型分组显示缩略图，明确标注属于套几、哪类型；每张可单独删除。
5. **本套文字要求 / 本套出图张数**：每套卡片内独立输入。
6. **开始生成**：校验每套都至少有 1 张产品图 → 触发工作流（第 6 章）。

### 3.4 校验（提交前）
- 每套 ≥1 张产品图，否则拦截并提示是哪套缺。
- 模特/场景可为空。
- 出图张数 ≥1。
- 目标市场必选。

## 4. 可复用的底层原语（直接调，别重造）

> 这些是 live 壳层已验证可用的底层能力，V2 直接复用。签名以当前代码为准。

### 4.1 出图任务提交 —— `createInternalJob`
文件：`src/services/internalApi.ts:1497`
旧买家秀 `submitBuyerShowImageJob`(`src/adapters/shellWorkflow.ts:1054`)就是封装它。新实现照抄这个封装，`module` 仍用 `BUYER_SHOW`：

```ts
const { job } = await createInternalJob({
  module: AppModule.BUYER_SHOW,      // 仍是买家秀，不新增模块
  taskType: 'kie_image',
  provider: 'kie',
  payload: {
    imageUrls,          // 本张图的输入图 URL 数组（产品/模特/场景/基准图）
    prompt,             // 本张图的提示词（来自策划阶段）
    ...taskMetadata,    // 归属元数据：setIndex、是否基准图、套内序号等
    model: config.model || 'gpt-image-2',
    aspectRatio: config.aspectRatio === AspectRatio.AUTO ? 'auto' : config.aspectRatio,
    resolutionMode: config.resolutionMode,
    targetWidth: config.targetWidth || 0,
    targetHeight: config.targetHeight || 0,
    maxFileSize: config.maxFileSize || 2,
    resolution: String(config.quality || '1K').toUpperCase(),
    kieClientConfigPresent: Boolean(input.apiConfig?.kieApiKey),
    requestId: `${Date.now()}-${Math.random().toString(36).slice(2,10)}`,
  },
  maxRetries: 2,
});
return { jobId: job.id };
```
返回 `jobId`；后端队列(`server/jobManager.mjs`)负责真正调号池出图、轮询、回写结果。**V2 不用自己写出图轮询**。

### 4.2 素材上传 —— `uploadShellMaterial`
文件：`src/adapters/shellWorkflow.ts:763`。把本地文件传到对象存储/公网可访问 URL，供出图时作为 `imageUrls` 传给号池。V2 每次用户选图后调它，拿 URL 落进对应套/类型。

### 4.3 策划阶段 —— 复用/仿写 `generateBuyerShowPrompts`
文件：`src/services/arkService.ts:1562`
签名：
```ts
generateBuyerShowPrompts(
  productUrls: string[],
  referenceUrl: string | null,   // 场景/氛围参考（优先），给策划做视觉锚点
  state: BuyerShowPersistentState,
  apiConfig: GlobalApiConfig,
  setIndex: number = 0,          // 用于多套"发散思维"，避免各套雷同
```

关键点：

- `state.imageCount` 决定这套要几张方案。
- 每套的第 1 张是**基准图**，后续图片依赖基准图保持一致性。
- 返回 `ArkBuyerShowResult`（含 `tasks[]`，每个 task 一段 prompt）。

> V2 可以直接复用这个函数（它只依赖入参，不耦合旧 UI），也可以基于它新写一个 V2 版策划函数。**推荐先直接复用**，跑通后再按 V2 需求微调 prompt。
> 策划底层的通用 AI 请求是 `requestAnalysisResponse`（arkService.ts 内），可复用。

### 4.4 结果展示 —— `ProjectListView`

**展示逻辑（业主定稿）：一套图 = 一个正常的项目任务卡，沿用现状 `ProjectListView`，不做特殊布局。** V2 把每套结果组织成一个 project，交给 `ProjectListView` 正常渲染即可。

## 5. 数据结构

参考旧类型 `src/types.ts`（`BuyerShowTask`:981 / `BuyerShowSet`:998 / `BuyerShowPersistentState`:1006）。重写时定义干净的新类型（**最终替换掉旧类型**；开发期若怕冲突可临时加后缀，替换后去掉），要点：

```ts
// 单张任务
interface BuyerShowV2Task {
  taskId: string;
  setIndex: number;        // 属于哪套（稳定，不随删除重排）
  indexInSet: number;      // 套内第几张
  isBenchmark: boolean;    // 是否本套基准图（第1张）
  prompt: string;          // 策划产出的提示词
  imageUrls: string[];     // 出图输入图
  jobId?: string;          // 出图任务 id
  resultUrl?: string;      // 出图结果
  status: 'pending' | 'planning' | 'submitted' | 'done' | 'failed';
}

// 单套
interface BuyerShowV2Set {
  setIndex: number;              // 稳定标识
  productUrls: string[];         // ≤5，必选
  modelUrl: string | null;       // ≤1，可选
  sceneUrls: string[];           // ≤4，可选（旧代码 atmosphere）
  setText?: string;              // 本套文字要求
  imageCount: number;            // 本套出图张数
  benchmarkUrl?: string | null;  // 本套基准图
  tasks: BuyerShowV2Task[];
}

// 整次持久化状态
interface BuyerShowV2State {
  targetCountry: string;   // 全局市场
  includeModel: boolean;   // 全局含模特开关
  sets: BuyerShowV2Set[];  // 单一真相，别再同时存 tasks[] 和 sets[]
}
```

> **P6 教训：旧 `BuyerShowPersistentState` 同时存 `tasks[]` 和 `sets?[]`，两份数据漂移。V2 只保留 `sets[]` 作为单一真相**，需要平铺任务时从 `sets[].tasks` 现算。

> **归属 setIndex 必须稳定**：删除中间某套后，展示序号可以重排，但已生成结果和持久化里的 `setIndex` 不能变，否则结果和套错位（旧 P1/P3）。建议 `setIndex` 用递增不复用的稳定 id，展示序号单独算。

## 6. 生成工作流

参考 `runShellBuyerShowWorkflow`(`src/adapters/shellWorkflow.ts:1084`)，重写自己的干净工作流 `runBuyerShowWorkflow`（替换旧实现）。两阶段、**逐套独立**：

```
for 每一套 set in sets:            // 各套独立，一套失败不拖垮其他套
  ── 阶段A 策划 ──
  productUrls = set.productUrls
  referenceUrl = set.sceneUrls[0] ?? set.modelUrl ?? null   // 场景优先做锚点
  state = { targetCountry(全局), includeModel(全局), imageCount: set.imageCount, ... }
  result = generateBuyerShowPrompts(productUrls, referenceUrl, state, apiConfig, set.setIndex, signal)
  ── 关键：策划失败要 continue+重试，不能 throw 中断整个循环（旧 P 级 bug，已在 live 修过）──
  set.tasks = result.tasks

  ── 阶段B 逐张出图 ──
  for i, task in set.tasks:
    imageUrls = 组装(产品图 + 模特图 + 场景图 + (非首张时)基准图)
    { jobId } = createInternalJob({ module: BUYER_SHOW, taskType:'kie_image', payload:{ imageUrls, prompt: task.prompt, setIndex: set.setIndex, isBenchmark: i===0, ...} })
    task.jobId = jobId
    首张出图完成后，其 resultUrl 作为本套 benchmarkUrl，喂给后续张
```

并发：用一个并发池控制同时提交的任务数（旧 `runBuyerShowConcurrencyPool`:1023 可借鉴），并发数取 `apiConfig.concurrency`。

> **必踩坑规避（来自跨项目经验）**：
> - **号池"报错伪装成功"**：号池/中转有时把上游错误当正常回包返回。策划结果要过一道「内容是否不可用」判据（旧 `isAnalysisContentUnusable`，arkService.ts ~290，含 `UPSTREAM_ERROR_KEYWORDS`），命中就当失败重试，别把错误文案当方案存下去。
> - **策划循环单套失败**：`throw` 要改成 `continue` + 重试，保证"我要三套，别因为第二套挂了把三套全废"。
